# ForensicGuard

**Lightweight Digital Evidence Analyzer**

Open-source forensic triage tool. Give it a file, an image, an email or a link,
and it answers one question: **does this deserve a closer look?** It never opens,
executes or decodes what it analyses.

### ▶ [Open the live demo](https://forensic-guard-rspd.vercel.app)

![The ForensicGuard landing page, showing the logo, the headline "Descubra o que um arquivo realmente é", and counters for recognised formats, risk rules and backend tests](docs/screenshots/landing.png)

> **The demo's backend sleeps after 15 minutes without use.** The first request
> wakes it up and takes about a minute — the interface shows the progress and
> unlocks on its own. Nothing is broken; it is booting.

---

## What this project is

A full-stack application built as two independent services that only speak HTTP:

```
┌──────────────────────────────┐          ┌──────────────────────────────┐
│  Next.js 16 · React 19       │   HTTP   │  FastAPI · Python 3.12       │
│  deployed on Vercel          │ ───────► │  deployed on Render          │
│                              │          │                              │
│  statically generated,       │          │  stateless, no database,     │
│  one build per locale        │          │  evidence deleted on exit    │
└──────────────────────────────┘          └──────────────────────────────┘
```

The split is deliberate. The backend never renders a page and the frontend never
runs forensic logic, so either one can be replaced without touching the other —
and the API is usable on its own at `/docs`.

| | |
| --- | --- |
| **33** | file formats identified by magic bytes |
| **27** | risk rules, each carrying the evidence that triggered it |
| **320** | backend tests, fixtures generated byte by byte in code |
| **0** | network requests made against the evidence |

## Engineering decisions worth reading

These are the parts a reviewer is likely to care about.

**Evidence is read in 64 KB blocks, never loaded whole.** A 500 MB upload read
with `path.read_bytes()` is a denial-of-service vector against your own server.
Every reader goes through [`app/utils/streaming.py`](backend/app/utils/streaming.py).

**Images are never decoded.** `Image.open()` reads the header only — `.load()`,
`.convert()` and saving are never called. That is what neutralises decompression
bombs, which are harmless until a pixel is rendered.

**Nothing on the network is contacted.** URL analysis is purely structural.
Querying a suspicious address tells whoever built it that they are being
investigated, so the tool dissects the address instead of visiting it.

**Every score carries its evidence.** A number without a justification is an
opinion, not a finding — so each indicator ships the value that triggered it.
The tool never states that something *is* malware.

**Layers with an enforced direction.** `routes → services → analyzers → utils`.
The test for whether a layer was respected: a module in `utils/` must work when
copied into any other Python project, unchanged.

**Limits are visible when they bite.** When a ceiling truncates the analysis,
the response says so. A forensic report must not imply it examined everything.

**Tests check external truth, not the implementation.** Hashes are verified
against published NIST vectors and entropy against known mathematical extremes —
not against whatever the code happens to produce.

**No binaries in the repository.** Test fixtures are generated byte by byte in
code. Nobody should have to download a suspicious file to clone a forensic tool.

## Privacy

| | Running locally | Hosted demo |
| --- | --- | --- |
| Where the analysis runs | your machine | a server on Render |
| Does the file leave your machine | **no** | yes, it is uploaded |
| Stored anywhere | no | no |
| Account required | no | no |
| Deleted after analysis | yes, including on failure | yes, including on failure |

The hosted demo exists so the tool can be tried without installing anything. If
the file you want to analyse is sensitive, run it locally — the instructions
below take about two minutes.

In both cases there is no database, no account and no history. The evidence is
written to a temporary file with a generated name and removed in a `finally`
block, so a crash mid-analysis does not leave it behind.

packages, no compiler. The project installs and runs identically on Windows,

## Analysing a file

The API is usable without the interface. Open http://127.0.0.1:8000/docs,
expand **POST /analyze**, click *Try it out*, pick a file and execute.

From the command line:

```bash
curl -X POST http://127.0.0.1:8000/analyze -F "file=@suspicious.jpg"
```

The response reports what the file is, what it claims to be, and what was
found inside it:

```json
{
  "filename": "invoice.jpg",
  "file": {
    "size": 234,
    "entropy": 5.11,
    "hashes": { "md5": "...", "sha1": "...", "sha256": "...", "sha512": "..." }
  },
  "detection": {
    "evidence_type": "file",
    "declared_extension": ".jpg",
    "detected_name": "Windows executable (PE / MZ)",
    "detected_category": "executable",
    "confirmed_bytes": 2,
    "mismatch": "executable_disguised"
  },
  "strings": {
    "total": 6,
    "returned": 6,
    "truncated": false,
    "sample": ["powershell.exe -windowstyle hidden -EncodedCommand ..."],
    "artifacts": {
      "urls": ["https://cdn.malicious-example.com/stage2.bin"],
      "ipv4": ["203.0.113.45"],
      "suspicious_keywords": ["powershell.exe", "-encodedcommand"]
    }
  },
  "risk": {
    "score": 100,
    "level": "critical",
    "indicators": [
      {
        "id": "file.executable_disguised",
        "title": "Executable disguised as another file type",
        "description": "The file content is an executable program, but its name suggests a document, image or other harmless type...",
        "severity": "critical",
        "score": 50,
        "evidence": {
          "declared_extension": ".jpg",
          "detected_type": "Windows executable (PE / MZ)",
          "confirmed_bytes": 2
        }
      }
    ]
  },
  "disclaimer": "ForensicGuard performs static triage based on indicators and heuristics..."
}
```

The evidence is written to a temporary file with an internally generated name
and deleted as soon as the analysis finishes — including when it fails.

### Size limits

| Limit | Default | Why |
| --- | --- | --- |
| Upload | 1 GB | Hashing, entropy and type detection read in 64 KB blocks, so memory stays flat regardless of file size. |
| Email parsing | 64 MB | The only part that needs the whole file in memory: the parser builds the full MIME tree before anything can be read from it. |
| String scanning | 8 MB | Strings worth reading appear near the beginning. The result reports when it was truncated. |
| Attachment | 10 MB each, 20 max, depth 2 | Keeps a nested message from expanding without bound. |

Change the upload limit in `backend/.env`:

```ini
MAX_UPLOAD_SIZE=1073741824
```

Oversized uploads are rejected with `413`, and the interface checks the size
before sending so you get both numbers — the file's and the limit's — instead
of a vague failure.

## How the risk score works

The score is the sum of every indicator that fired, capped at 100.

| Score | Level |
| --- | --- |
| 0 – 20 | low |
| 21 – 50 | medium |
| 51 – 75 | high |
| 76 – 100 | critical |

**Every indicator carries the evidence that triggered it.** That is the whole
point: a number without a justification is an opinion, and a forensic report
cannot be an opinion. Each entry tells you which rule fired, how many points
it added, and the concrete data behind it — so you can check the conclusion
yourself, and disagree with it.

Two design choices worth knowing about:

- **High entropy only counts when it is unexpected.** Archives, images and
  video are compressed by nature and always score close to 8. Flagging them
  would fill every report with noise and teach you to ignore the score. The
  indicator fires on text, documents, executables and unrecognised formats.
- **A disguised executable raises two indicators**, not one: it is both an
  extension mismatch (35) and a disguised executable (50). They are two
  distinct observations about the same fact, and each is explained separately.

All weights and thresholds live in a single file,
`backend/app/constants/risk_rules.py`. No score is written anywhere else in
the codebase.

Email indicators — SPF, DKIM, DMARC, sender mismatch — arrive with the email
analyser. See [`docs/roadmap.md`](docs/roadmap.md).

## Image forensics

When the evidence is an image, the response gains an `image` section with
dimensions, colour mode, EXIF metadata, the device that took the photo, the
software that edited it, and GPS coordinates converted to decimal degrees.

```json
"image": {
  "width": 4032,
  "height": 3024,
  "megapixels": 12.19,
  "image_format": "JPEG",
  "device_make": "Apple",
  "device_model": "iPhone 15 Pro",
  "software": "Adobe Photoshop 25.1",
  "created_at": "2026:10:15 09:12:00",
  "gps": { "latitude": -22.12, "longitude": -51.39 }
}
```

Two things this deliberately does **not** treat as findings:

- **A photo without EXIF.** Every social network strips metadata on upload, so
  most images in circulation have none. Absence of EXIF is the normal case.
- **Editing software.** Most professional photography passes through an
  editor. `Adobe Photoshop` in the metadata is information, not an accusation.

GPS raises an indicator worth **zero points**. Embedded location does not make
a file dangerous — it makes the person who shared it exposed. The indicator
exists to warn, not to accuse.

### Reading hostile images safely

Images are never decoded. `Image.open()` reads only the header, and the code
never calls `.load()`, `.convert()` or anything else that would touch the
pixels.

That matters because of **decompression bombs**: a file of a few hundred bytes
whose header declares tens of thousands of pixels per side. Decoding it would
demand gigabytes of memory and take the service down. Reading only the header,
the bomb never goes off — and the attempt still gets reported:

```json
{
  "id": "image.decompression_bomb",
  "severity": "high",
  "score": 25,
  "evidence": { "file_size_bytes": 68, "pixel_limit": 250000000 }
}
```

## Email forensics

An `.eml` file is the message exactly as it travelled: headers, a blank line,
and the body. The response gains an `email` section with the headers, the
`Received` chain, the authentication verdict, every link, and the attachments.

The most important fact about email analysis is this: **almost every header is
written by whoever sent the message.** `From`, `Reply-To`, `Subject` and `Date`
are not verified by anything — forging a sender is trivial. The fields that
carry evidentiary weight are `received_chain` and `authentication`, because
those are added by the servers the message passed through.

### What gets checked

| Check | Why it matters |
| --- | --- |
| SPF / DKIM / DMARC | Read from `Authentication-Results`. The receiving server already did the verification; repeating it over DNS would need network access and would judge an old message against today's records. |
| Reply-To and Return-Path domains | A reply or a bounce going somewhere other than the sender's domain. Newsletters do this legitimately, so the weight is modest. |
| Link text vs destination | `<a href="http://evil.example">www.banco.com.br</a>` — the defining technique of phishing. Neither the text nor the URL reveals it alone. |
| Attachments | Each one is written to a temporary file and runs through the **same** pipeline as the main evidence, with its own risk score. |

### Recursive attachment analysis

An attachment named `fatura.pdf` whose bytes start with `MZ` is reported as a
disguised executable, with its own `critical` score, nested inside the email's
report:

```
phishing.eml                     RISK 100  CRITICAL
  Reply-To    ...@gmail.com      <- different domain
  SPF fail | DKIM fail | DMARC fail
  LINK  shows "www.empresa.com.br" -> http://203.0.113.45/login
  ATTACHMENT fatura.pdf
      declared: application/pdf
      detected: Windows executable (PE / MZ)
      RISK 100  CRITICAL
```

Recursion is capped at depth 2 and 20 attachments. Without a limit, an email
containing an email containing an email would descend until the stack or the
disk ran out. Attachments beyond the limit are still listed — hiding them
would be worse than not analysing them.

## Deploy

The two services are deployed independently, which is the point of keeping them
apart. Reproducing the setup takes two free accounts and no configuration files.

### Backend — Render

| Setting | Value |
| --- | --- |
| Root Directory | `backend` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `uvicorn app.main:app --host 0.0.0.0 --port $PORT` |
| Health Check Path | `/health` |

`--host 0.0.0.0` is not optional: without it Uvicorn listens on loopback only,
the deploy reports success, and every request times out. `$PORT` is assigned by
the platform — a fixed port does not work.

| Environment variable | Value | Why |
| --- | --- | --- |
| `PYTHON_VERSION` | `3.12.8` | Unpinned, the platform picks its own and changes it without notice. `requirements.txt` pins every package with `==` for the same reason |
| `MAX_UPLOAD_SIZE` | `26214400` | 25 MB. The default is 1 GB, which assumes the tool is running on your own machine against your own disk images |
| `CORS_ORIGINS` | the frontend URL | Origin only — no path, no trailing slash |

### Frontend — Vercel

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| Framework Preset | Next.js (detected) |
| `NEXT_PUBLIC_API_URL` | the backend URL, no trailing slash |

`NEXT_PUBLIC_*` is baked in at build time, not read at runtime, so changing it
requires a new deployment.

### Two details that are easy to get wrong

**The order.** Vercel needs the Render URL and Render needs the Vercel URL, so
deploy the backend first, then the frontend, then come back and set
`CORS_ORIGINS`.

**The cold start.** A free Render service sleeps after 15 minutes of inactivity
and takes about a minute to return. The frontend handles this explicitly: it
distinguishes *starting* from *offline*, shows the progress, keeps retrying on
its own and unlocks the upload area when the server answers. Calling a sleeping
server "offline" would be the interface lying about its own state.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `python` opens the Microsoft Store | Windows placeholder. Use `py` instead, or install Python from python.org with "Add to PATH" ticked. |
| `Error: Command '...venv' returned non-zero exit status 1` on Debian/Ubuntu | `python3-venv` is missing. Run `sudo apt install python3-venv`. |
| `Python 3.12+ is required, but this is 3.11` | Older interpreter. Use `py -3.12 dev.py` on Windows or `python3.12 backend/dev.py` on Linux. |
| PowerShell refuses `Activate.ps1` | Execution policy. Run `Set-ExecutionPolicy -Scope Process RemoteSigned`, or just use `python backend\dev.py`, which needs no activation. |
| Page shows **API offline** | The backend is not running, or it is on a different port. Confirm http://127.0.0.1:8000/health responds. |
| `EADDRINUSE` / port already in use | Another process holds the port. Use `python backend/dev.py dev --port 9000`, or stop the other process. |
